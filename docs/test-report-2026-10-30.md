Дата: 30 октября 2026 года. Полный worker join не выполнялся.

| Узлы | два исходных Worker; оба Ready до и после теста |

сохранялись. Kubeconfig не копировался на VDS или в тестовый Pod.

Для внешнего теста использовался тестовый WireGuard-интерфейс `k8nprobe0` и
сеть `10.203.73.0/24`. VDS слушала UDP 31821, тестовый Pod — 31820,

и hostPath. Сетевые настройки существующих Worker, Calico IPPool и адреса узлов
не менялись. Поля Kubernetes в inventory внешнего транспортного теста являются
синтетическими фикстурами для конструктора текущего драйвера, а не описанием
совместимости настоящего k0s/Calico-кластера с kubeadm/Flannel.

## Найденная и исправленная ошибка

Первый запуск на реальном Linux остановился на добавлении peer route:
`Device for nexthop is not up`. Драйвер поднимал интерфейс после установки
маршрутов. Теперь после ключей, адреса и защитного blackhole-маршрута интерфейс
поднимается до добавления peer routes. Порядок компенсаций при ошибке сохранён.

Тестовая модель ядра дополнена тем же ограничением. После исправления прошли
`go test -race ./...`, `go vet ./...`, сборка и оба реальных транспортных теста.

## Подтверждение очистки

- В Kubernetes нет оставшихся namespace с префиксом `k8nnect-`.
- Оба исходных узла остались Ready с прежними InternalIP/ExternalIP.
- На VDS нет тестовых интерфейсов, маршрутов протокола 242 или network namespace.
- Временные каталоги внешнего теста с приватными ключами удалены.
- На VDS остались установленный пакет `wireguard-tools` и каталог
  `/root/k8nnect-lab-20261030` с бинарником, архивом и Linux-тестом; приватных
  ключей в этом каталоге нет. Сервис агента не устанавливался и не запускался.

## Что этот результат не подтверждает

VDS не зарегистрирована как Kubernetes Node. Ни один workload не планировался
на VDS через Kubernetes Scheduler. Внешний тест проверяет транспорт и его
жизненный цикл в изолированных сетях, а не поддержку k0s/Calico самим продуктом.

Для полноценного сценария остаются отдельные задачи:

1. Реализовать профиль k0s + Calico VXLAN Always, сохранив текущие Node IP и
   владение маршрутами со стороны Calico.
2. Определить bootstrap для managed k0s при доступе только через Kubernetes API.
   Предоставленный административный kubeconfig не является worker join token.
   Обычный `k0s token create` использует локальное состояние контроллера;
   генерация bootstrap через API и существующие RBAC/CSR-механизмы пока не
   реализована и в этом тесте не проверялась.
3. Проверить достижимость API и konnectivity из внешнего Worker, а также обратные
   пути CNI; открытого Kubernetes API недостаточно для всей сетевой интеграции.
4. Использовать Calico IPAM как источник реальных аллокаций: Node.spec.podCIDR
   здесь отличается от наблюдаемых Calico-блоков и адресов Pod.
5. Проверить worker join, Ready, scheduling, Pod-to-Pod, DNS, сервисы, exec/logs,
   перезагрузку VDS, разрывы сети и ограничение доступа.

Транспортный тест не является тестом отказоустойчивости всего Kubernetes и не
измеряет предельную пропускную способность или производительность шифрования.
